# Keys belong to the person, not a team

Ships with the user-keys plan. SSH and signing keys, and how a workspace pod gets its
`authorized_keys` file, both move off the fixed `user-key` Secret.

## What moved

| what | before | after |
|---|---|---|
| key ownership | `Credential.owner` could be a team | `Credential.owner` is always the person's email; `/v1/keys` 400s a body carrying `owner` |
| git-over-SSH identity | resolved off the URL's owner | resolved off the fingerprint: `auth/sshkey/{fp}` → email, then `App::may_act(user, owner)` checks own handle or team membership through the directory (60 s cache, fails closed on `Source::Unavailable`, `user == owner` on a solo node's `Source::Absent`) |
| workspace pod's authorized_keys | fixed `user-key` Secret, written by the api into every namespace the owner's workspaces live in | `OwnerKeys` CR (one per owner namespace, named by the handle) the api projects and the agent converges to `{pool}/keys/{owner}/authorized_keys`, mounted read-only at `/home/kl/.ssh/authorized_keys` |

Why: a team-owned key meant revoking a departing member's access required rewriting every key
row they'd touched; a person's keys living in one place, checked at use, means revoke is one
delete. The Secret also had to be rewritten into every namespace a workspace could land in
(the same fan-out problem team-namespaces already hit) — the CRD-plus-agent-converge shape used
for `resolv.conf` attach files covers it without a rename fan-out.

## Rollout

Server tier, then agents, then the api — agents and api back to back, in one sitting.

- **Server first.** It reads the fingerprint row, and a row that still names a handle is judged by
  the pre-migration rule (`App::may_act` admits a handle for its own namespace only), so a server
  ahead of the migration locks nobody out.
- **Agents next.** A node on this build mounts `{pool}/keys/{owner}/authorized_keys`, which only
  the api writes an `OwnerKeys` for. So on such a node a default-image workspace START parks in
  `Creating`/`KeysNotReady` until the api's first projection lands — seconds once the api is up
  (the create projects its owner directly), at most one `KEYS_RESYNC_SECS` (300 s) otherwise.
  Pods already RUNNING are unaffected: their file is already mounted. This is why the agents and
  the api go back to back rather than a day apart.
- **Api last.** Its boot runs the migration below and its beat writes every projection.

Through all of it the `user-key` Secret keeps its `authorized_keys` entry, so a pod on a node whose
agent has NOT been upgraded still admits the same keys. That entry is dropped in the release after
every region's agent is on this build (spec §5 step 4) — nothing else reads it.

## The marker

A document `{_id: "keys_v2"}` in the directory's `meta` Mongo/Cosmos collection
(`MongoCollections.meta`, database `kloudlite` at `KLOUDLITE_MONGO_URI`) — not the object store;
the directory is where team/person ownership lives, so that is where its own migration state
lives too. `Directory::migrate_keys_to_people` runs once at api boot, rewrites every team-owned
`SshKey`/`SigningKey` row to `created_by`, and returns the `(email, fp)` pairs so `main.rs` can
re-index them with `store.add_ssh_key` — the fingerprint index has to be rebuilt under the new
owner before anything reads it. Only once both steps succeed does `mark_keys_migrated` write the
marker document. A failure partway aborts boot: an api that came up with rewritten rows but no
marker, or a marker with no rewrite, is worse than one that never started, so the restart just
redoes the whole pass. Idempotent either way — re-running finds rows already on `created_by` and
no-ops them.

## How to verify

```sh
# The CR side: every owner namespace should show a recent generation and Synced=True once the
# agent has had one reconcile.
kubectl get ownerkeys

# The person's own view, unaffected by which physical file backs it:
curl -H "Authorization: Bearer $TOKEN" https://<server>/v1/keys
```

A `Synced=False` row that doesn't clear points at the agent for that owner's node — check its
`status` conditions (`NoKeys`/`WriteFailed`) before assuming the api side is wrong; the api's own
health is the migration marker below plus normal `/v1/keys` writes succeeding.

## How to re-run the migration by hand

Only needed if the rewrite or the fingerprint re-index needs to run again against object-store
state restored from a backup, or a bug is found and fixed after the marker already landed.

```sh
# Delete the marker document from the directory, then restart the api —
# migrate_keys_to_people re-runs at the next boot. Safe to repeat: rows already on
# created_by are left alone.
mongosh "$KLOUDLITE_MONGO_URI" --eval 'db.getSiblingDB("kloudlite").meta.deleteOne({_id: "keys_v2"})'
kubectl rollout restart deployment/kloudlite-api
```

The superadmin Clusters area does not yet surface `OwnerKeys` sync state — `kubectl get ownerkeys`
is the only view until that lands; noted as deferred against spec §4.
