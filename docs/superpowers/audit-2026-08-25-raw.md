# 1. Security Audit — rustic-git

Scope: `crates/{core,storage,gitbase,pulls,registry,workspaces}`, `bins/{server,agent,api}`, focused on authn/authz, injection into object-store keys and shell commands, secret leakage, and routing/ownership handling.

## Findings

### 1. CRITICAL — Container/host escape via unsanitized environment mount `folder`

**File:** `crates/workspaces/src/engine/compose.rs:41`, `bins/agent/src/lib.rs:569`, validated only at `crates/workspaces/src/api.rs:536`

A `Mount.folder` (`crates/workspaces/src/model.rs:199`) is user-supplied and validated **only** for non-emptiness (`create_env`, api.rs:536: `m.folder.is_empty()`). It is then used two ways, both without path validation:

- `bins/agent/src/lib.rs:569` — `std::fs::create_dir_all(live.join("volumes").join(&m.folder))`
- `compose.rs:41` — `let vol_dir = live.join("volumes").join(&m.folder);` then emitted as a docker-compose bind source `"{vol_dir}:{m.path}"`.

`Path::join` with an absolute component **discards the base**: `live.join("volumes").join("/etc")` resolves to `/etc`. A relative `../../../..` traverses out equally. So an authenticated user (any account with a username) creating an environment with a service mount like:

```json
{"services":[{"name":"x","image":"alpine","mounts":[{"folder":"/","path":"/host"}]}]}
```

causes the agent — which runs **as root on the btrfs host** — to bind-mount the host root filesystem read-write into a container whose image the same user chose. That is arbitrary host file read/write, i.e. full compromise of the agent node.

**Exploit:** create environment → agent `EnvUp` renders compose with `/:/host` bind → user's container reads/writes host `/`, e.g. drops an SSH key in `/root/.ssh` or edits `/etc`.

**Fix:** reject any `folder` that is not a single safe path segment — reuse `rustic_git_storage::store::valid_segment` (already forbids `.`, `..`, `/`, and non-`[A-Za-z0-9._-]`). Enforce at `create_env` (like the empty check) AND defensively in `mkdir_env_mounts`/`render` before the join. `m.path` (container target) is inside the container and less critical, but validating it too is cheap.

### 2. LOW/MEDIUM — vol-agent tokens are fleet-wide, not region-scoped (documented)

**File:** `bins/server/src/vol_agent.rs:84-99` (`authorized`), noted in the module's own `// ponytail:` at lines 10-13.

The record routes (`commits`/`ref`/`history`) accept **any** registered region's `agent_token` (or a break-glass token) to write **any** volume's records, unscoped by the volume's owning region. A leaked agent token from region X can rewrite region Y's volume commit history / move refs. This is explicitly acknowledged as a v1 trusted-operator-fleet decision, so I flag it only for the ledger. The job routes (`region_by_token`) are correctly scoped; the constant-time compares (`peer::secret_eq`) and empty-token guards throughout are correct. Upgrade path is already written in the ponytail comment (scope to the volume's owning region).

## Checked and found solid

- **JWT (`crates/core/src/jwt.rs`)** — HS256 pinned explicitly (`alg:none`/key-confusion covered by a test), `validate_exp` on, `typ` discriminates session vs registry tokens by rule not accident, secret length floor of 32 bytes, subject normalized. Registry-token scope deliberately not trusted (re-authorized per request). Good.
- **Registry auth (`crates/registry/src/auth.rs`)** — Basic requires username==resolved owner (leaked token can't be used under another name), anonymous vs invalid credential distinguished correctly, private-image anonymous gets challenge / authenticated stranger gets 403, `write` never treats an image as public. Solid.
- **Credential storage (`crates/storage/src/auth.rs`)** — tokens stored as SHA-256 keys (never plaintext), bounded negative cache defeats spray-amplification, revocation immediate on the acting node, poison-tolerant lock. Good.
- **`Digest::parse` / `Hasher` (`crates/registry/src/store.rs:28`)** — strict algo allowlist (sha256/sha512), exact length, lowercase-hex only; it is the only path from a URL segment to an object key (`blob_path`/`manifest_path`), so no traversal reaches the store. Client-claimed algo is never trusted to pick a hash.
- **Git smart-HTTP auth (`bins/server/src/router/git.rs`)** — owner-or-public model (`storage::auth::authorize`), visibility checked via object store before opening/creating a DB (prevents anonymous pool-warming), 401 vs 403 distinction correct. No team-collaborator write path exists yet (documented ponytail), so no bypass there.
- **Peer secret compare (`crates/core/src/peer.rs:22`)** — constant-time, empty never matches, length-guarded. Hop-by-hop header stripping and `MAX_HOPS` bound present in the forwarder.
- **Shell-outs (agent `container.rs`, engine `ops.rs`, `compose.rs`)** — all use `Command::new(argv[0]).args(...)`, no shell interpolation, so no classic command injection. Workspace/env **ids are server-generated** (`rid()` = prefix + random hex), so ids used as path/argument components are safe. Argument-injection via a leading-`-` value (image name, container name) is not reachable to a meaningful payload because each is a single argv slot and can't smuggle a second token; `docker run` places the user image last but a single `-`-prefixed value just fails to supply an image. (Finding #1 is the exception because it's a filesystem-path join, not an argv token.)
- **Body limits** — git `max_body` (2 GiB, enforced in the extractor pre-handler, `httpx.rs:76`) and the registry's separate `max_layer`/manifest limits exist as the CLAUDE.md contract describes.
- **Owner/name namespace** — `valid_owner`/`valid_segment` reject `.`/`..`/`/` and reserved owners (`api`,`v2`,`img`,`vol`); vol-agent route parsing (`vol_agent.rs:48`) re-validates and rejects reserved owners.

**Top priority: fix #1** — it is remotely reachable by any authenticated workspace user and lands on a root agent.

# 2. Rustic-Git Systems Audit (architecture and correctness)

Auditor's note: this is an unusually well-defended codebase. The stated invariants in CLAUDE.md are, with very few exceptions, actually upheld in code — most named races already have a dedicated test and a specific mitigation. Findings below are the genuine residual gaps; the great majority are low-severity hardening notes. No critical bugs found. Panics on request paths are essentially nonexistent (every `unwrap`/`expect` outside `#[cfg(test)]` is either a startup fail-closed, a `Mutex::lock` poison-propagation, or on a compile-constant).

---

## Findings

### Merge subsystem

**M1 — Lease-lapse double-worker can record a landed merge as "Failed" (Medium)**
`crates/pulls/src/merge_worker.rs:499-514`, `bins/server/src/browse_api/pulls.rs:489-518`, lease `crates/app/src/lib.rs:439` (`MERGE_LEASE = 10min`).
Worker A claims PR #5; its merge outruns the 10-min lease; the owner re-announces and worker B claims it. Both computed the same merge from the same `base_oid`. A's `push --force-with-lease` wins and the ref moves — the change *is* merged. B's push then fails the lease, and B (the current claimant) records `Outcome::refused`, so the PR shows **Failed/Refused despite having actually merged**, and `HeadMoved`/`PullMerged` events never fire (sibling PRs aren't re-checked). Self-heals only on a later retry via the `is-ancestor` guard (`merge_worker.rs:431`).
Fix: on a push failure, re-resolve the base and re-run the `is-ancestor` / squash tree-equality check before recording Refused — a `force-with-lease` rejection where the head is already in the base is a Merged, not a Refused. Or renew the lease on a heartbeat rather than using a fixed 10-min window.

**M2 — Rebase committer date not pinned; contradicts the determinism invariant (Low)**
`crates/pulls/src/merge_worker.rs:595-600` vs the module claim at `:588-590` and `commit_tree` at `:548-562`.
`commit_tree` pins `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` so merge/squash retries re-mint identical commit ids; the rebase arm sets only committer name/email, so `git rebase` stamps `GIT_COMMITTER_DATE = now`. Rebased ids are therefore non-deterministic, contradicting the "a retried rebase re-mints identical commits" comment. No live duplicate today (rebase retry self-heals via patch-id skipping), but two concurrent workers (M1) produce divergent rebase results.
Fix: pass `--committer-date-is-author-date` (or set `GIT_COMMITTER_DATE`) on the rebase invocation.

**M3 — `claim_merge` (scan variant) omits the `state == Open` guard (Low, currently dead code)**
`crates/pulls/src/pulls/jobs.rs:51-76` vs `claim_merge_number:104-105`.
`claim_merge_number` refuses a non-Open PR; the scan-based `claim_merge` checks only merge-job `takeable()`, so it would claim a queued merge job on a Closed/Merged PR. Exported via `pub use jobs::*` but has no callers.
Fix: delete `claim_merge` (YAGNI — the worker only claims by number), or add the same `pr.state != Open` short-circuit.

**M4 — Permanently-erroring merge re-announces forever (Low, acknowledged)**
`merge_worker.rs:395-399`, `bins/worker/src/main.rs:337-345`, `jobs.rs:118-155`.
A merge returning `Err` (unwritable cache, always-failing fetch) never POSTs an outcome, stays `Running`, lease lapses, and `stranded_merges` re-announces every 30s indefinitely — retry count is unbounded. Acknowledged in comments.
Fix (optional): an `attempts` counter on the job; after N, mark `Failed` with a "retry manually" detail so it stops being takeable.

Stale comment: `api_pull_check` doc says "Always 204" (`pulls.rs:359`) but returns `Json(deep)`/500. Harmless.

### Registry

**R1 — `manifest_cache.lock().unwrap()` is process-wide poison-fragile (Medium)**
`crates/registry/src/manifests.rs:179,280,309,384`, `store.rs:428`. Every manifest GET/PUT/DELETE unwraps the same `std::sync::Mutex`; one panic while held cascades every subsequent manifest request into 500s. Holders only do map ops today (so the trigger is unlikely), hence Medium.
Fix: `lock().unwrap_or_else(|e| e.into_inner())` (a poisoned cache is still valid data), matching the pattern `storage/src/auth.rs` already uses for its neg-cache; or `parking_lot::Mutex`.

**R2 — A legitimate manifest with a non-digest `"digest"` string is rejected (Low)**
`manifests.rs:133-143`: `gc::collect` grabs every JSON value keyed `digest` anywhere in the doc; a parse failure returns `MANIFEST_INVALID` 400. A manifest carrying an annotation literally keyed `digest` with a non-digest value is refused on push. Asymmetric with GC, which only over-collects (safe).
Fix: filter unparseable strings here instead of erroring.

**R3 — No in-crate re-validation of owner/name (Low, defense-in-depth)**
Registry write handlers interpolate `owner`/`name` straight into object-store keys, trusting `route_inner` (`route.rs:312-317`) to have run `image_route`'s validation. Correct today and covered by `every_browse_route_is_routable`, but the handlers would build unsanitized keys if ever mounted without that middleware. Cheap hardening: a `valid_owner`/`valid_segment` guard at the top of the write handlers.

(The `put_manifest`→GC blob-existence TOCTOU is real but already `ponytail:`-documented at `manifests.rs:115` and mitigated by GC keep-bias + double-`referenced()` read.)

### Storage / pool / fencing

**S1 — `now_ms()` panics on a pre-1970 clock (Low)**
`crates/storage/src/ownership/mod.rs:29-34` — `.expect("system clock before 1970")`, on the claim/renew/force-claim request path. A container starting at epoch 0 before NTP would panic the handler.
Fix: `unwrap_or_default()` — a zero clock makes leases look expired and routes to the claim path instead of crashing.

**S2 — `max_warm` is a soft target, not a hard ceiling (Low, by design, untested)**
`crates/storage/src/pool/evict.rs:17-22,52`. `evictable` skips any entry still referenced (`strong_count > 1`), so under a burst where every warm DB has a live request, nothing is evictable and `warm_count` exceeds `max_warm` unbounded until requests drain. This deliberately subordinates the memory cap to never closing a DB under a live request, but the ceiling gap is untested (`pool_stays_within_max_warm` only covers the sequential case).
Fix: none needed for correctness; add a `ponytail:` comment documenting the soft-target trade, and optionally backpressure new-repo opens above a hard multiple.

**S3 — Synthesized fence in `adopt` can flap a sibling's healthy handle (Low, already `ponytail:`-flagged)**
`crates/storage/src/pool/lease.rs:88-98`. When an evict removes a slot mid-open, `adopt` returns `FencedError` and `App::on_fenced` evicts blindly by key, which can close a fresh handle a concurrent caller just reopened. Self-healing (one extra flap).
Fix (as the comment says): have `on_fenced` evict only when the slot's own handle reports `close_reason.is_some()` (reuse `evict_if_same` semantics).

## What's well-designed (verified, not assumed)

- **Ownership routing** (`bins/server/src/router/route.rs`): the pre-auth routing middleware genuinely refuses every path it cannot route rather than letting it fall through to a handler that would open a DB — `/api/`, `/v2/`, and `/vol-agent/` prefixes each have an explicit "shape matches but unroutable ⇒ refuse" branch, and `is_git_route` distinguishes "not ours" from "ours but malformed". The three keyspaces (`{owner}/{name}`, `img/…`, `vol/…`) use disjoint prefixes backed by `RESERVED_OWNERS`, so they cannot collide. `every_browse_route_is_routable` and the vol-agent equivalent scrape the router source and assert against the tail lists — the test that would have caught the historical `imagetags` bug.
- **Push path** (`crates/git/src/protocol/receive.rs`): full connectivity+isolation walk that refuses "exists in local odb" (the cache can hold objects the repo doesn't own), quarantine-delete of the just-uploaded pack on any rejection, fence-propagation vs per-ref-report separation, a `Capped` BufRead that errors rather than truncates, a 1 GiB per-object alloc cap against zlib/delta bombs, and strict ref-name validation with a table test.
- **Merge idempotency**: deterministic commit ids (author/committer taken from the head commit, fixed `+0000`) make a retried merge land as a no-op; `is-ancestor` and `tree == base_tree` guards cover ff/merge and squash retries; `force-with-lease` uses the base oid the merge was computed *from* with the server doing the CAS (no TOCTOU). Peer secret leakage is genuinely prevented — the `local()`/`networked()` split is respected and no argv carrying `http.extraHeader` is ever formatted into an error.
- **Registry invariants all hold**: only client-DELETE and the GC sweep delete blobs; the sweep aborts (never `continue`s) on any unreadable/unparseable manifest and double-reads the referenced set; manifests are stored/returned verbatim; every path→key conversion goes through a validated `Digest`; three distinct body limits.
- **Pool concurrency**: `OnceCell` single-flights opens, `evict_if_same` keys on the exact `Arc<Db>` pointer, `close_all` re-checks `strong_count` under the map lock, the `std::sync::Mutex` is always dropped before any `.await`, and every unbounded structure (keyed locks, auth/manifest caches, events stream `MAXLEN 5000`) has a bound.

## Architecture

- **Crate boundaries are clean.** `storage` depends only on `core`; `git`/`registry`/`pulls` layer above `storage`; the three binaries compose them. The `pulls` `check` feature is correctly enabled only in `bins/server` and off in `bins/worker`/`bins/api`, keeping the DB-directory dependency out of the worker. The one cycle (`workspaces` → `bins/server`) is a **dev-dependency**, explicitly commented as such — fine.
- **No dead-code sprawl**: zero `TODO/FIXME`, only 2 `#[allow(dead_code)]`, and technical debt is tracked as 219 structured `ponytail:` markers rather than rotting comments. The one live dead-code item is M3 (`claim_merge`).
- **Duplication is minimal and deliberate**: the two `routing_key` functions (`registry` `img/`, `workspaces` `vol/`) are distinct keyspaces, not copy-paste.
- **Worth doing**: (1) fix M1 — it's the one finding with user-visible wrong state; (2) unify the `Mutex::lock().unwrap()` pattern on the manifest cache to the poison-tolerant form the auth cache already uses (R1); (3) delete `claim_merge` (M3). Everything else is optional hardening.

# 3. Workspaces/Environments Subsystem Audit

Scope: `crates/workspaces`, `bins/agent`, `bins/api`, `bins/server/src/vol_agent.rs`, verified against `tests/ws_e2e.sh`.

---

## Critical

### C1. Mount folder path traversal — bind-mounts arbitrary host paths into user containers
- `/Users/karthik/rustic-git/crates/workspaces/src/api.rs:536` only rejects an **empty** `Mount.folder`. `/Users/karthik/rustic-git/bins/agent/src/lib.rs:569` does `create_dir_all(live.join("volumes").join(&m.folder))` and `/Users/karthik/rustic-git/crates/workspaces/src/engine/compose.rs:41` renders `live/volumes/{folder}:{path}` into docker-compose.
- Scenario: `{"folder":"../../../../etc","path":"/host"}` escapes the env's subvolume and bind-mounts the agent host's `/etc` (agent runs as root) RW into a user-supplied image. Full host compromise. `folder` containing `:` also corrupts the compose volume string (`m.path` is unvalidated too — a crafted `path` can append `:ro`-style options or a second mapping).
- Fix: validate `folder` as a single safe path segment (same `valid_segment` used for owners/names — it already exists in `rustic_git_storage::store`), reject `/`, `..`, `:`; validate `path` as an absolute, colon-free path. Enforce at the API trust boundary, and defensively in `mkdir_env_mounts`/`render`.

### C2. `Workspace.volume`/`Environment.volume` is never written — env re-materialization is dead code, and the arguments are swapped anyway
- No production code assigns `volume: Some(...)` (only test fixture `crates/workspaces/tests/api_volumes.rs:91`). `model.rs:86` and the e2e's `wait_ws_pushed` comment claim "the job-done handler writes `volume` after first push" — no such handler exists in `/Users/karthik/rustic-git/bins/server/src/vol_agent.rs` (`job_done` only flips ws/env state).
- Consequence: `EnvUp`'s recovery branch `match &env.volume { Some(r) => pull_env(...) }` (`bins/agent/src/lib.rs:514-517`) can never fire. An environment whose local subvolume is gone (pool wipe, node replacement, or a completed `EnvDelete` followed by a re-create-by-name workflow) is silently rebuilt as an **empty** subvolume even though its pushed history exists in the registry — the user's data appears lost.
- And when someone does wire the pointer, the call is wrong: `engine.pull_env(&env.id, r)` at `lib.rs:516` passes `(owner=env.id, id="vol/{owner}/{id}")` against the signature `pull_env(owner, id)` (`crates/workspaces/src/engine/ops.rs:507`) — it would query a nonexistent registry keyspace and fail.
- Fix: in `job_done` set `volume = Some(routing_key(owner, id))` on first successful `Push`/`WsCreate`/`EnvDown`; change the `EnvUp` call to `pull_env(&owner, &env.id)` (the payload already carries owner). Alternatively drop the pointer and key the recovery branch on "registry history non-empty".

### C3. Any agent in a region can lease a job the scheduler deliberately left unassigned — owner binding is not enforced at lease time
- `/Users/karthik/rustic-git/bins/server/src/vol_agent.rs:396`: `j.agent.as_deref().is_none_or(|a| a == q.agent)` — a queued job with `agent: None` is leased by **whichever agent polls first**.
- `agent: None` is not just "about to be scheduled": the scheduler intentionally leaves it `None` when the owner's bound agent is dead (`crates/workspaces/src/scheduler.rs:388` "re-homing is a migration, not something the scheduler decides"), and the requeue sweep clears `j.agent = None` on every expiry (`crates/workspaces/src/lease.rs:31-33`). Either way, agent B leases work whose subvolumes live on agent A's pool: a `WsPush` on B snapshots a nonexistent live subvolume (fails, burns retries → workspace marked Error), a `WsClone` falls back to the registry path and materializes the workspace on the wrong node, splitting the owner's data across two pools while the binding says otherwise.
- Fix: in `work`, only lease jobs where `j.agent == Some(q.agent)`. Unassigned jobs should wait for `schedule()`/the sweep to place them; the "unclaimed" arm defeats the entire binding design.

### C4. 120s fixed lease + no shell-out timeouts ⇒ routine double execution, and non-idempotent jobs then fail spuriously
- Lease is a hardcoded 120s (`vol_agent.rs:400`); jobs shell out to `docker run` (image pull), `btrfs send` of multi-GB deltas, Azure uploads — easily minutes. None of the `Command` shell-outs in `ops.rs`, `compose.rs`, `container.rs` has a timeout, and there is no lease-renew heartbeat per job. The sweep (`lease.rs:24-34`) requeues an expired-but-still-running job; the binding sends it back to the *same* agent, which now runs it **concurrently with itself** (the semaphore allows 4 in flight; `ws_lock` serializes push but not `docker run`/compose).
- Concrete non-idempotency: a retried/duplicate `WsCreate` calls `create_subvol` → `btrfs subvolume create` on an already-existing `live` fails (`ops.rs:166-171`), a retried `WsClone` snapshots into an existing `live(dst)` path and fails (`ops.rs:624-630`); three such "failures" mark a perfectly healthy workspace `Error` (`vol_agent.rs` `mark_ws_error`). Worse: after 3 lease expiries a *still-running, ultimately successful* job is marked `Failed` by the sweep.
- Fix: per-job lease renewal from the agent (a heartbeat on `jobs/{id}` extending `lease_until`), or lease scaled to job kind; make `create_subvol`/clone tolerate an existing `live` (idempotent replay), and put timeouts on shell-outs so a hung docker doesn't pin a blocking thread forever.

## High

### H1. Stale/duplicate completion reports corrupt job state — `job_done`/`job_failed` don't check lease ownership or current state
- `/Users/karthik/rustic-git/bins/server/src/vol_agent.rs` `job_done` (~line 545) and `job_failed` (~570) load the job and overwrite state unconditionally. After a lease expiry + requeue: attempt 2 succeeds (`Done`), then attempt 1's late failure report flips the job back to `Queued` → a **third** execution of, e.g., `WsDelete` or `EnvDown` (each `EnvDown` retry appends another push/commit). Conversely a late `done` from a superseded attempt marks a requeued job `Done` while nobody ran it.
- Fix: `job_failed`/`job_done` should no-op unless `job.state == Leased && job.agent == <reporting agent>` (the agent id is derivable — send it as a query param like `work` does).

### H2. Sweep-exhausted jobs never mark the doc Error — workspace stuck in `creating` forever
- `lease.rs:33` sets `JobState::Failed` after retries but never calls `mark_ws_error`/`mark_env_error` (those run only from the `job_failed` HTTP path, `vol_agent.rs` exhausted branch). A dead agent's `WsCreate` exhausts via the sweep → the workspace doc stays `Creating` forever; the e2e's `wait_ws_state` would poll to timeout with no `error` signal, and users see a permanent spinner.
- Fix: call the mark-error helpers from the sweep's exhausted branch (move them into `crates/workspaces` next to `sweep`).

### H3. Deleted workspace resurrected to `Ready` by an in-flight clone/create — env has the guard, ws doesn't
- `mark_env_state` (`vol_agent.rs:~508`) explicitly refuses to overwrite `Deleted` ("delete wins"). `mark_ws_ready` (`vol_agent.rs:433`) has **no such check**: delete a workspace while its `WsCreate`/`WsClone`/`WsRestore`/`WsStart` job is leased → job completes after `WsDelete` ran `cleanup_local` → doc flips to `Ready` with no volume behind it, reappearing in listings as a live workspace.
- Fix: mirror the env guard — `if w.state == WsState::Deleted { return }`.

### H4. Team-owned environment volume history reads the wrong registry keyspace
- `volume_history`/`volume_refs` (`crates/workspaces/src/api.rs:809,830`) call `get_history(&owner, &name)` where `owner` is the **caller's username**, but `owns_volume` (`api.rs:783-798`) grants access to a team env via team membership — whose commits were pushed under `vol/{team}/{envid}` (`push_job` uses `e.owner`). A team env's history/refs always come back empty for every member.
- Fix: have `owns_volume` return the actual owning namespace and pass that to `get_history` (same pattern `find_env` already uses).

### H5. `set_lineage` is a non-atomic, panicking write — a crash mid-write loses unpushed data via the janitor
- `/Users/karthik/rustic-git/crates/workspaces/src/engine/pool.rs:98-101`: `std::fs::write(...).unwrap()`. (a) ENOSPC/EIO panics the whole agent (or the job thread) instead of failing one job. (b) truncate-then-write with no tmp+rename: a crash mid-write leaves a truncated/empty `.lineage`; the `unpushed` marks — the **only** record that staged data exists — are gone, so the next janitor tick (`bins/agent/src/lib.rs:294-305`) sees the staged blobs as unreferenced and deletes them. That is the only local copy of unpushed data: permanent loss.
- Fix: write to `{name}.lineage.tmp` then `rename`; return `Result` instead of unwrap.

### H6. Janitor stage sweep races an in-flight commit — it doesn't take `ws_lock`
- `commit_core` writes the staged blob/meta (`ops.rs:206,225`) *before* appending the `unpushed` lineage entry (`ops.rs:230-231`). The janitor reads lineage files without `ws_lock` (`lib.rs:240-251`); a tick landing in that window computes `keep` without the new blob and `janitor_sweep_stage` deletes the freshly staged file — the subsequent `upload_core` fails on the missing stage file, and after the mismatch a retried push fails forever on `std::fs::read(stage_meta_path)` (`ops.rs:260`). Low probability (600s tick) but it's the exact "fail forever on a missing stage file" the upload comment promises can't happen.
- Fix: either reverse the order (append lineage first, then stage — with a matching orphan rule), or have `janitor_sweep_stage` skip files younger than, say, one hour, or take `ws_lock` per volume when unioning.

## Medium

### M1. `EnvDelete` leaks the compose project dir and is non-idempotent
- `cleanup_local` (`lib.rs:628-671`) removes `vol/{id}` but never `{pool}/env/{id}` (`env_dir`, `lib.rs:557`): every deleted environment leaves a rendered `docker-compose.yml` dir behind forever.
- `compose::down` (`compose.rs:78`) requires the compose file to exist — an `EnvDelete` for an env never brought up on this pool (or a retry after a partial first attempt) fails at `down`, and the retried `push_env` then fails on the missing live subvolume (`commit_core` snapshot of nonexistent path), so the delete job exhausts retries with local state half-cleaned.
- Fix: in `EnvDelete`, tolerate a missing compose file/subvolume (skip down/push when absent) and `remove_dir_all(env_dir)` at the end. Same file-missing tolerance for `EnvDown`.

### M2. Block image files leak: squash and block-restore never delete `{pool}/img/{blob}.img`
- `squash_inner` creates the image (`ops.rs:820`), uploads it, and never removes the local file — one workspace-sized file leaked per auto-squash. `pull_core`'s block path keeps the image mounted (legit) but `cleanup_local` only umounts and `remove_dir_all(voldir)` — the `.img` under `pool/img/` survives delete. The janitor never sweeps `img/`. Unbounded pool growth.
- Also `ops.rs:842`: if `umount` of the throwaway `/tmp/wssquash-{id}` mount fails, the mount and dir leak (and `/tmp` on a read-only-root pod is its own hazard given the deploy notes).
- Fix: `remove_file(&img)` after `upload_stream` in squash; sweep `img/*.img` not referenced by any lineage/mount in the janitor.

### M3. Stale squash latch permanently disables auto-squash
- `upload_core` skips spawning when `{id}.squashing` exists (`ops.rs:328-343`); the latch is removed only by a squash child that runs to `Engine::squash` (`ops.rs:792-797`). If the spawned child dies before that (bad env, `meta_store_from_env` failure, OOM-kill, `owner_file` missing → `squash()` errors before engine.squash — `bins/agent/src/main.rs:692-711` errors out without touching the latch), the latch stays forever and every future push reports "already running". Chains then grow unboundedly past `chain_max`.
- Fix: treat a latch older than N hours as stale (mtime check) or write the child PID and check liveness.

### M4. Restarted agent with a stale persisted id bricks itself
- `register` (`lib.rs:111-141`) reuses `{pool}/agent-id` unconditionally; `work` 404s an unknown agent id (`vol_agent.rs:~390` `ok_or_else(job_not_found)`). If the agent doc is gone (Cosmos db recreated, region rebuilt — exactly what the e2e does per run), the agent loops "work poll: 404" every 5s forever instead of re-registering.
- Fix: on a 404 from `work`, delete the id file and re-register.

### M5. No validation on `create_ws`/`create_env` inputs; nonexistent region ⇒ silent forever-`creating`
- `create_ws` (`api.rs:262-283`) accepts any `region` string; `schedule` finds no agents, and the sweep only iterates **registered** regions (`vol_agent.rs` `spawn_sweep` over `store.regions()`), so a job in a typo'd region is never re-scheduled and the workspace sits in `creating` with no error, ever. `name` is unvalidated (empty, 10MB, control chars), `quota_gb` is accepted but never enforced anywhere in the engine (no btrfs qgroup) — a declared 5GB workspace can fill the pool.
- Fix: 400 on unknown region and on empty/oversized names; either enforce quota via `btrfs qgroup` or drop the field from the API until it does something.

### M6. Job docs, commit history, and lineage grow without bound; no pagination anywhere
- Jobs are never deleted or TTL'd (nothing calls a delete in `store.rs`/`cosmos.rs`); `queued_jobs`/`leased_jobs` are full-partition queries the work long-poll runs **every second per agent** (`vol_agent.rs:392`) — Cosmos RU burn grows linearly with job history unless the query filters state server-side *and* is indexed (it filters, but the doc count still grows forever). `history` (`crates/workspaces/src/registry.rs:798-809`) scans and returns every commit ever — `/v1/volumes/{name}/history` is unpaginated, and `push` on `EnvDown` appends a commit per stop. `list_ws`/`list_env`/`list_volumes` likewise unpaginated.
- Fix: Cosmos TTL on done/failed jobs (built-in TTL field — one line in the container spec); `?limit=`+continuation on history and lists.

### M7. No per-volume job ordering
- Two jobs for one workspace (e.g. `Push` queued right after `WsCreate`, or `WsDelete` racing `WsClone`) can be leased into different slots of the 4-way semaphore and run concurrently/reordered — Cosmos query order is unspecified. `ws_lock` serializes lineage writes but not `docker`/compose/delete-vs-clone interleavings; the source-deleted-mid-clone case degrades to retries→`Error`.
- Fix: skip leasing a job whose payload volume id already has a leased job (one query), or serialize per-volume in the agent dispatcher.

### M8. Unverified `restore` source ownership vs. deleted docs — minor API polish
- `push_ws`/`start_ws`/`stop_ws`/`clone_ws` happily operate on a `Deleted` workspace doc (tombstones remain readable, `api.rs:720` etc.) — the queued job then fails against missing local state and burns agent cycles; return 409/404 for terminal states. `delete_ws` on an already-`Deleted` doc re-enqueues a second `WsDelete`.

## Low

- `LineageEntry::parse` (`model.rs:145-167`) indexes `p[1]`/`p[3]` without length checks — a corrupt/truncated lineage line panics the agent. Return a `Result` or skip bad lines.
- `uuid()` (`ops.rs:119-121`, `fsck.rs`) unwraps `/proc/sys/kernel/random/uuid` — fine on Linux, but a panic path; `expect` with a message at minimum.
- `is_mountpoint` (`pool.rs:155-158`) string-compares against `/proc/self/mounts`; paths containing spaces are octal-escaped there and won't match — a pool mounted at a path with a space silently misclassifies block-restored voldirs (then `snap_root` picks `recv/` and cleanup skips the umount).
- `pull_core` first-chunk handling (`ops.rs:416-427`): `d[0]` on a possibly-empty first stream chunk panics; and if the object-store stream yields a 0-byte first chunk the mode byte is misread. Guard `d.is_empty()`.
- Break-glass `authorized` for volume record routes accepts **any** region's token for **any** volume (documented ponytail at `vol_agent.rs:10-14`) — acknowledged, but note it also means a compromised region token can *overwrite the `main` ref* of every workspace fleet-wide, which is a data-integrity blast radius, not just confidentiality.
- `agent_token` returned only on region create but `create_region` rotates nothing and echoes the stored token to any admin re-POSTing — fine, but the token also transits `regions()` into `authorized`'s loop on every request; consider caching.
- `tests/ws_e2e.sh` defines `wait_ws_pushed` but never calls it — dead helper masking the missing `volume`-pointer writer (C2); the script would not have caught it.
- Agent `report()` failure (`lib.rs:328-330`) just logs — the job stays leased until the sweep expires it (acceptable given the sweep, but note it inflates `attempts` for a job that succeeded).

## What's solid

- The staged-push crash-recovery seam is genuinely well done: cleanup strictly after `post_commits` + `move_ref` (`ops.rs:302-315`), re-upload/re-POST idempotent by blob id, and the `unpushed` mark discipline is consistent across clone/restore/squash.
- Cross-volume sharing guards (`other_unpushed_blobs`, `other_lineage_snap_names`, `lib.rs:586-626`) correctly close the delete-source-strips-clone's-parent class of bugs, and the janitor's keep-bias (never touch unpushed) matches the storage rules elsewhere in the repo.
- Registry design — full-lineage-per-commit records (no inter-record deps), immutable content-addressed blobs, single-writer SlateDB giving `move_ref` its ordering for free — is clean and matches the OCI registry's discipline.
- Shell-outs use argv arrays throughout (no shell interpolation, no quoting bugs); the `clone_running` "start must run even if snapshot/push failed" contract is handled carefully on every path, including compound error reporting.
- The scheduler's binding CAS (`bind_owner` conflict-adopt) and the token-hygiene in `RegistryClient` (fixed-string errors, never a formatted reqwest error) are both correct and well-reasoned.

Top priorities: **C1** (host escape), **C3/C4** (lease/binding — these will bite in the first real deployment), **C2** (env data loss), then H5/H6 (the two paths that can destroy the only copy of unpushed data).

# 4. rustic-git performance audit

Three parallel deep-reads across git protocol, registry/storage, and the API/worker/agent/web tiers. Verified the git pack path (`crates/git/src/protocol/upload/{mod,pack,walk}.rs`) and the HTTP entry (`bins/server/src/router/git.rs`) first-hand; the rest comes from the sub-audits. Findings are ranked globally by impact.

## Critical / High impact

### H1. Chunked blob upload is O(N·K) — re-streams the whole partial layer per chunk
`crates/registry/src/uploads.rs:280-296` (also completion re-read at `:434-444`)
Each `PATCH` opens a full GET of the staging object and rewrites all of it plus the new chunk via a fresh multipart. A 10 GiB layer pushed in 100 MiB chunks moves ~1 TiB each way through the node. Completion then re-reads the whole staged object again just to hash it. The two `ponytail:` notes at `:275` and `:390` already name it.
Fix: persist the S3 multipart upload-id + part list in a sidecar (`uploads/{o}/{n}/{uuid}.parts`); `PATCH` calls `UploadPart` for its own bytes only (S3's 5 MiB min matches OCI), `complete` does `CompleteMultipartUpload`. Kills both findings.

### H2. No SlateDB object-store or block cache configured anywhere
`crates/storage/src/pool/mod.rs:143-149`, `ownership/mod.rs:193-223`
Flush/compactor/GC are tuned but `object_store_cache_options` and block-cache size are left at defaults, and the default in-memory block cache is split across `max_warm=64` DBs. Every SST block miss on every warm repo/image DB is an S3 GET — this sits under every `tag()`, `image_is_public`, referrer scan, and ref read. Single biggest lever for metadata latency. `RUSTIC_GIT_CACHE_DIR` is currently used only for git packs.
Fix: point SlateDB's on-disk cache at a subdir of `RUSTIC_GIT_CACHE_DIR` with a byte budget and set an explicit shared block-cache size against the pod memory limit.

### H3. `reachable_set` = full-repo object enumeration on every incremental fetch
`crates/git/src/protocol/upload/mod.rs:183,215` → `walk.rs:250` (`ours`)
Any fetch that sends a `have` (all real clients do) triggers a `TreeContents` walk over every object in the repo before a byte of pack is produced. Memoized per-fetch only. A `have` is always a commit, so the closure is not needed.
Fix: use the commit traversal alone for the have-path; keep the full object set only for the non-tip promisor want. O(objects)→O(commits). Then cache per `(repo, tip-set)` as the `mod.rs:336` note suggests.

### H4. 25 redundant `git fetch`es per base-branch push (merge worker)
`crates/pulls/src/merge_worker.rs:629` + `bins/worker/src/main.rs:271-273`
One `HeadMoved` fans out to up to `CHECK_LIMIT=25` diverged PRs; each `check_one` re-runs a full network `sync()` fetch against the fleet, into the same cache dir, under the same per-repo merge lock. 25 round trips where 1 suffices, serially, blocking the repo's merge lane.
Fix: split `sync` out of `check`/`run` so the caller fetches once with the union refspec (`fetch` already builds refspecs), then the 25 calls become local `merge-tree`. Optionally `buffered(4)` the now-local runs.

### H5. Agent long-poll spends ~90 Cosmos ops per agent per 30 s at idle
`bins/server/src/vol_agent.rs:385-412`
Each of ~30 iterations per poll window does 3 Cosmos ops — including a heartbeat **write** (5× the RU of a read) and `agents_in()` which fetches every agent doc only to `.find()` one. That is the dominant idle cost of the workspace control plane.
Fix: heartbeat once per window (90 s alive threshold gives 9× margin at a 10 s beat); replace `agents_in().find(id)` with the existing `read_item` point read; keep 1 s only on `queued_jobs`.

### H6. Requeue sweep runs on every replica, unguarded
`bins/server/src/vol_agent.rs:603-616`, spawned at `bins/server/src/boot.rs:39-41`
Every pod runs a cross-partition `regions()` + job queries + per-job `schedule()` every 30 s, all CAS-racing each other, so N−1 replicas' work is wasted.
Fix: one line — `if app.is_leader()`, matching the prune lane at `lanes.rs:81-83`. Idempotent + CAS-guarded, so correctness is unaffected.

### H7. Agent 204 branch has no sleep floor
`bins/agent/src/lib.rs:185-187`
Safe only because the server holds the poll 30 s. Any short-idle-timeout proxy, test config, or the 503 path turns `continue` into a network-speed busy-spin; both error branches already sleep 5 s.
Fix: one line — `sleep(1s.saturating_sub(elapsed))` before `continue`.

## Medium impact

### M1. receive-pack: one full closure walk per pushed ref + a full-repo walk
`crates/git/src/protocol/receive.rs:263,285` — `reachable_set_hiding` runs once per updated ref with the same hide set; a 20-branch push walks it 20×. 10-20× on multi-ref/mirror pushes.
Fix: one batched `reachable_set_hiding(all_new_tips, old_tips)`, attribute per-ref only on the rare error path.

### M2. Rejected pushes upload the full pack to S3 before validating it
`crates/git/src/protocol/receive.rs:228-238` (checks at `:263`, delete at `:307/:319`) — a broken/hostile client makes the server pay a full multipart upload+delete per rejected push. The pack is already on disk and indexed before upload.
Fix: run the connectivity check before `upload_pack_files`.

### M3. `repack` writes the pack twice and never re-deltas
`crates/git/src/gc.rs:155-163` — temp file, then `Bundle::write_to_directory` re-reads/re-indexes the whole thing (2× IO, 2× zlib). Worse, it goes through the fetch path's `PackCopyAndBaseObjects` (`pack.rs:134`), so repack consolidates file count but never shrinks the repo — the point of repack. It also inherits the gix#2935 merge workaround it doesn't need.
Fix: `pack_from_ids(odb, tips, TreeContents, …)` directly, pipe instead of temp-file, and a delta-computing mode on this path only.

### M4. `manifest_stat` does a full prefix LIST per manifest push
`crates/registry/src/manifests.rs:210` → `store.rs:317-336` — a multi-arch push = N+1 full LISTs of a forever-growing prefix.
Fix: keep manifest count/newest as counters in the image DB, incremented by the writing push; leave the LIST for the GC reconcile that has no DB.

### M5. `Pool::exists` LISTs S3 per request when cold
`crates/storage/src/pool/mod.rs:203-217` — funnels `tag()`, `image_is_public()`, `image_exists()`; every anonymous pull of a cold/evicted image costs a LIST.
Fix: small TTL cache keyed `{owner}/{name}`; the answer only flips on create/delete, both local.

### M6. `grant_renew` holds the global leader lock across N serial store ops
`crates/app/src/lib.rs:589-600` — a node with 200 warm repos holds the process-wide lock for 400 serialized get/put while `grant_claim` (cold-repo request path) queues behind it. This is the warm-count↔claim-latency coupling.
Fix: take/release the lock per repo inside the loop (preserves per-CAS atomicity), or shard via the existing `Store::keyed_lock`.

### M7. `regions()` cross-partition query on every agent request
`crates/workspaces/src/cosmos.rs:145-147`, called from `work`/`done`/`failed`/`register`/`list_regions`/sweep — `SELECT *` with `PartitionKey::EMPTY` for a set the code calls "small, fixed".
Fix: 30-60 s TTL cache (copy `neg_cache` in `app/src/lib.rs:181`).

### M8. Janitor blocks the reactor and is O(V²)
`bins/agent/src/lib.rs:228-256` (blocking `read_dir` + `btrfs subvolume delete` in a plain `tokio::spawn`) and `:270`/`:613` (re-scans all of `vol/` and every other volume's lineage once per volume). On a shared multi-tenant VM V grows with tenants.
Fix: wrap the tick in `spawn_blocking` (functions already split); build the snap-name set once before the loop.

### M9. Serial per-team point reads in workspace API (4 sites)
`crates/workspaces/src/api.rs:499,581,764,784` (`find_env`, `list_env`, `list_volumes`, `owns_volume`) — N independent reads run serially on every env/volume route; scales with team count.
Fix: `join_all`/`try_join_all`, one line each, semantics unchanged.

### M10. GC second `referenced()` pass runs even when nothing is doomed
`crates/registry/src/gc.rs:307` — steady-state `doomed` is empty yet a full second read of every owner manifest runs.
Fix: `if doomed.is_empty() { return Ok(0) }`.

### M11. gix#2935 merge workaround adds a whole-repo tree walk to any fetch containing a merge
`crates/git/src/protocol/upload/pack.rs:59-67`, `walk.rs:333-350` — not per-merge (merges are deduped into one `count_objects` call), but the ceiling is ~one extra full-repo `TreeContents` walk + an O(objects) dedup HashSet whenever the range has ≥1 merge commit. On a PR-merge repo that near-doubles clone CPU, silently.
Fix (without waiting on upstream): expand each merge against its first parent only, diffing trees with the existing `browse.rs changed_files` two-list merge, feed the new ids as `AsIs` leaves. O(changed paths).

### M12. `queued_jobs` unbounded, caller takes first match
`crates/workspaces/src/cosmos.rs:123-133,255` — `try_collect()` drains all pages; `vol_agent.rs:396` then `.find()`s the first. Called every second per agent.
Fix: `SELECT TOP 20 … WHERE state='queued'`.

### M13. `open_repo` marker reconcile on every git request
`crates/storage/src/store.rs:321-343` — `is_public` get + `reconcile_marker` (2 object GETs, possibly a write) per request, to repair a crash window, while the pack fetch it's compared against is usually a no-op `stat`.
Fix: rate-limit per repo like `prune_stale_packs`'s `.pruned` marker.

## Low impact (batch these opportunistically)

- **Serial deletes** → batch with `WriteBatch`/`delete_stream` (already the pattern elsewhere): `registry/store.rs:392-403`, `referrers.rs:66-79`, `storage/store.rs:509-546`.
- **Unbounded listing fan-out** → `buffer_unordered(16)`: `registry/routes.rs:22-43`, `index.rs:207-214`.
- **`bump_pulls` read-modify-write + lock on the hottest pull path** (`registry/store.rs:281-296`) → in-process `AtomicU64` flushed by the sweeper.
- **git browse micro-allocations**: `last_changes` recomputes the tree it already has each iteration (`browse.rs:286`); `entries_of`/`files_at` hex-encode→parse oids twice per entry (`browse.rs:124`); `diff_trees_inner` copies each blob 3× (`browse.rs:560`); `merge_base`/`is_ancestor` uncached 50k walks per compare/protected-ref (`gitbase/merge_base.rs:22`, `refs.rs:58`).
- **`deepen-not` LISTs refs per arg** (`mod.rs:118`) → hoist `all_refs`.
- **`check_one` fan-out serial** after H4 fix (`worker/main.rs:271`); **`merge_worker::prune` sync IO on the gc lane** (`main.rs:444`) → `spawn_blocking`.
- **`repo_meta` 4 sequential DB gets** (`refmeta.rs:255`) → `tokio::join!`.
- **`engine/ops.rs`** blocking work behind `async fn` signatures — safe today (only called under `spawn_blocking`), but a fragile contract worth a comment.

## What's already well-optimized (leave alone)

- **Pack bodies stream** on both fetch (`pack.rs:141` `FromEntriesIter`) and push (`receive.rs` indexes straight from the socket via `Capped`); S3 up/downloads stream in 5 MiB parts. The one caveat: the HTTP handler buffers request+response in `Bytes` (`router/git.rs:202` — flagged `ponytail:`), and `count_objects` materializes a `Vec<Count>` for the whole pack before first byte (H-adjacent; cap clone concurrency).
- **Blob sizes read from object headers, never by inflating** (`browse.rs:147`, `walk.rs:107`) — the documented 15.2 ms→0.2 ms win.
- **Fetch traversal computed once** and shared between include-tag and the pack (`mod.rs:261`); `ours()` memoization collapses have+want checks.
- **Auth is correctly cached** (60 s hit+miss, bounded sweep, `storage/auth.rs:48`); JWT path does zero IO.
- **No lock held across await** anywhere in the pool/store/cache — every `std::sync::Mutex` guard verified dropped before the next await.
- **Manifest cache, streaming blob GET, concurrent blob-existence probes, single-scan `tags_pointing_at`** in the registry.
- **`crates/pulls/src/check.rs`** — `open_repo` hoisted out of the per-PR loop, tips compared before the walk, 50k-budget `spawn_blocking`, re-read under lock. Strongest file in the audit.
- **Bare merge cache reused** with incremental fetch + narrowed refspec; **agent dispatch** is a clean semaphore + per-job runtime loop; **per-lane task split** in `lanes.rs` (encodes a real starvation incident).
- **Web BFF is the healthiest tier**: no per-item N+1, `react cache` placed exactly where it dedups cross-route work, `Promise.all` on independent calls, `no-store` the right default. Only nit: a 5-10 s `revalidate` on `getRepo` in `guardRepo` if the api tier shows hot.

## Cheapest wins first
H6 (one line, `is_leader()` guard) and H7 (one line, sleep floor) remove latent runaways for near-zero diff. H5 is a hoist + point read. H2 is config only. H1 and H4 are the biggest wins but need the sidecar / `sync`-signature refactors respectively.

# 5. Audit report: rustic-git (web app + Rust workspace)

Reviewed at branch `restructure` (3cc61cf). Severity: **High** = fix soon, real exposure or debt near its ceiling; **Med** = worth scheduling; **Low** = polish.

---

## Part 1 — Next.js app (`web/apps/web`)

### Auth / session / token exposure — overall: strong, no leaks found

The design is unusually careful and correct:

- The API bearer token is deliberately kept **out** of the session object (`src/auth.ts:165-170` explicitly does not copy `token.apiToken` into `session`), and server code reads it back from the encrypted JWT via `getToken` in `src/lib/api-token.ts`. `/api/auth/session` therefore never exposes the credential to client script. Verified: no client component imports `api.ts` (it is `server-only`), and `PEER_SECRET` is used in exactly one server-side path (sign-in).
- The passkey credentials provider (`src/auth.ts:48-61` + `src/lib/assertion.ts`) correctly defends the public Auth.js callback URL: it accepts only a 60-second HMAC (`timingSafeEqual`, length-checked) minted server-side after WebAuthn verification. The preview password provider uses a constant-time compare and an allowlist. Both are documented with the threat model in comments.
- Cookie `Secure` handling is derived once from `AUTH_URL` (`src/auth.ts:100-101`) and shared with `api-token.ts` — good single source of truth.

Findings:

1. **[Low] `secureCookies` silently downgrades if `AUTH_URL` is unset** — `src/auth.ts:100`. The comment acknowledges it ("deploy yaml sets it"), but a misdeployed pod ships a non-Secure session cookie with no warning. Fix: `console.error` (or refuse in production `NODE_ENV`) when `AUTH_URL` is missing/non-https.
2. **[Low] Token re-mint failure is only `console.error`** — `src/auth.ts:155`. A session can exist with no `apiToken` and every page then renders "signed out"-ish states. Handled downstream by the `/login?from=expired` redirect, but the jwt callback swallows the reason; consider stamping a `tokenError` claim so the UI can distinguish "directory down" from "expired".

### Server actions input validation — acceptable, with one systemic note

3. **[Med] Actions trust `formData` for `owner`/`repo` and rely wholly on the API server for authorization** — e.g. `src/app/(shell)/[owner]/[repo]/settings/actions.ts:10-38` (and the same shape in `pulls/actions.ts`, `edit/actions.ts`, etc.). This is a sound trust boundary *if* the API enforces ownership on every route (spot-checked `crates/api/src/repos.rs` — it does authorize). But the actions also feed the raw strings into `revalidatePath(`/${owner}/${repo}`)`; a crafted `owner` like `a/../b` revalidates an unintended path. Harmless today (cache invalidation only), but cheap to close: validate `owner`/`repo` against the same slug regex the API uses (or reuse `lib/reserved.ts`) before calling out. Why it matters: the day someone adds an action that uses these strings for anything besides an encoded URL segment, the missing validation becomes a bug.
4. **[Low] `destroyRepo` confirm check compares only against `repo`, not `owner/repo`** — `settings/actions.ts:80`. Two same-named repos under different owners get the same confirm string. GitHub uses `owner/name`; trivial change.

### XSS — clean

- The **only** `dangerouslySetInnerHTML` in the app is shiki output (`src/components/repo/code-block.tsx:12`), and shiki HTML-escapes code content. Grammar/lang is allowlisted through `fenceLang`/`langFor` (`src/lib/highlight.ts:83-88`), so a hostile fence name cannot select arbitrary input.
- The README renderer (`src/components/repo/code.tsx:23-49`) is a hand-rolled ~25-line markdown subset that emits **JSX text nodes**, never raw HTML — React escapes everything. PR bodies/comments render as `whitespace-pre-line` text (`src/components/repo/pull-conversation.tsx:16`). No `remark`/`marked` dependency to mis-configure. Good.
- **[Low]** The markdown subset silently drops links, images, `###`+, ordered lists, nested lists — a README with `[text](url)` shows literal brackets. Not a security issue, but users will notice; when you extend it, keep the emit-JSX-only property (never switch to an `__html` pipeline without sanitization).

### API error handling / loading states

- `src/lib/api.ts` is the pattern done right: one `call<T>` wrapper, typed `ApiResult` with `conflict` as a value not a throw, network failure mapped to a user-safe message (`api.ts:54-59`), 404-as-authorization documented. All 28 path interpolations use `encodeURIComponent` (verified by count vs. interpolation sites).
- Mutating forms consistently use `useActionState` with `pending` disabling (`delete-form.tsx:44` fieldset trick is nice, `new-repo-form.tsx:99`).
5. **[Med] Almost no route-level loading UI**: exactly one `loading.tsx` in the whole app (`app/(shell)/[owner]/[repo]/loading.tsx`) and one `Suspense` (`components/repo/file-view.tsx:129`). Every other navigation (dashboard, pulls list, image pages, settings) blocks on server fetches with no skeleton — on a slow API the app just freezes on the old page. Fix: add `loading.tsx` at `(shell)/` and `(shell)/[owner]/` at minimum; they're one-file additions.
6. **[Low] Error boundary coverage**: `app/(shell)/error.tsx` exists but `(auth)` and `(onboarding)` segments have none; a thrown fetch there hits the default Next error page.

### N+1 / fetch patterns in server components

- Generally good: `app/(shell)/page.tsx:28` uses `Promise.all`, and `components/repo/code.tsx:99-106` even speculatively fetches `README.md` in parallel with the tree listing to avoid a waterfall (with a correct fallback second fetch only for oddly-named READMEs). No `.map(async …)` per-row fetch loops found in any list component.
- The real N+1s live server-side in Rust and are marked (`crates/workspaces/src/api.rs:42,498`) — the web app is not the aggregator, which is the right shape.

### Accessibility

- Reasonable baseline: ~99 `aria-*`/`sr-only` usages, Radix primitives for dialog/dropdown/select/tooltip (accessible by construction), `aria-label` on icon-only controls sampled in `repo-list.tsx`, `app-shell.tsx`.
7. **[Low] PR comment list uses array index as key** (`pull-conversation.tsx:47-48`) — cosmetic until comments become editable/deletable, then it reorders state. Use a comment id when one exists.

## Part 2 — Rust workspace

### Error type design (`crates/core`)

9. **[Med] `Error = Box<dyn Error + Send + Sync>` + stringly `err(msg)` is the workspace-wide error type** — `crates/core/src/err.rs:1-6`. Consequences already visible: callers match on message substrings (`crates/storage/src/cache/disk.rs:64` matches `"BUSYGROUP"`; `crates/workspaces/tests/engine_ops.rs:276,316,570` assert on `"registry"`/`"history"`/`"sha mismatch"`; `bins/server/src/boot.rs:511-521` matches routing-error prose). Tests coupling to prose means an improved message breaks tests, and the BUSYGROUP match couples to redis crate internals. Fix (incremental, not a rewrite): where a caller *branches* on an error, introduce a small typed error for that seam only (a `#[derive(thiserror::Error)]` enum in `storage::cache` for the BUSYGROUP case; typed variants in `workspaces::engine`). The blanket `Box<dyn>` is fine everywhere nothing branches. Note `#![allow(clippy::result_large_err)]` at `lib.rs:1` — a boxed error is pointer-sized, so this allow looks vestigial; try removing it.

10. **[Low] One redundant clone** — `crates/pulls/src/merge_worker.rs:452` `head_oid.clone()` where a move works (confirmed by `clippy::redundant_clone`; the lint aborted compilation there under `-D warnings`, so re-run `cargo clippy --workspace -- -W clippy::redundant_clone` after fixing to catch any behind it). Otherwise the extra-lint pass was clean up to that point — clone discipline is good.

### Ponytail debt inventory (~90 markers; triaged)

The bulk (≈70) are `// ponytail: eprintln` — one homogeneous debt: **no structured logging anywhere** (`"swap for a logger when one exists"` appears in 5 crates). That's Med severity in aggregate: no levels, no repo/request correlation, and ops greps prose. Ceilings that look **close**, in order:
- **High**: `vol_agent.rs:10` region scoping (finding 13 — security).
- **Med**: `crates/registry/src/manifests.rs:113,147` — GC sweep can delete a blob between HEAD-check and manifest put (a TOCTOU the comment owns; a busy registry with aggressive GC will eventually eat a push). Med because the sweep is keep-biased and rare, but it's a correctness race, not a perf ceiling.
