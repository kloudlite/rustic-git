# Repo audit fix plan — 2026-08-29

**Scope.** The whole repository at master `8c0b4e0`: the Rust workspace (`crates/*`, `bins/*`, `tests/`), the web app (`web/apps/web`), and everything under `deploy/` and `.github/`.

**Method.** Five auditors worked independently, each with one lens, and wrote one report each (raw copies in `docs/superpowers/audits/2026-08-29/`): security (S), performance (P), Rust code quality (Q), web (W), infrastructure (I). A sixth pass then opened the cited code for every finding marked critical, high or bug — and for anything that sounded implausible — and recorded a verdict before ranking. Overlapping findings were merged into one item that keeps every source id, so an id in any raw report resolves to exactly one checkbox below.

**Totals.** S: 0 critical, 4 high, 9 medium, 27 low (40). P: 17 high, 24 medium, 12 low (53). Q: 5 bug, 13 high, 34 medium, 49 low (101). W: 3 high, 14 medium, 20 low (37). I: 6 high, 13 medium, 9 low (28). 259 findings in all.

**Verification outcome.** 43 findings were opened and checked (every high/bug plus 9 that sounded implausible). 41 were confirmed as written. One was refuted and dropped: **Q-4** (thin-pack push lifting a sibling fork's objects) — `Repo::odb()` is `gix_odb::at(objects_dir)` on `cache/{owner}/{name}/objects` (`crates/storage/src/store.rs:139-148`, "every repo owns its objects outright"); there is no shared fork-network odb any more, so a ref-delta base can only resolve against this repo's own cache. The residual case (a base in a rejected-push pack still in this repo's cache) exposes only objects that were already pushed to this repo. Two were downgraded: **P-6** ("one global lock across the renewal beat" — the lock is taken per repo, `crates/app/src/lib.rs:589-601`; the sequential durable puts remain, so it is medium, not high) and **P-9** (`referenced()` is already `buffered(16)`, `crates/registry/src/gc.rs:37-55`; only the reconcile fan-out is unbounded, so medium). The already-known S-1 was re-confirmed against `ws_namespace` (`crates/workspaces/src/crd.rs:610-617`): `ws-{team}-{owner}` joined by `-` with `-` legal in both handles.

Ranking inside each phase is severity × ease: the cheapest fix for the worst problem comes first. Items that should ship as one PR are grouped under a bold heading.

## P0 — exploitable or data-loss (fix this week)

**Vol-agent record surface** — one PR, `bins/server/src/vol_agent.rs` + `bins/server/src/router/mod.rs`

- [x] **Q-1** Forwarded `/vol-agent/*` writes are unauthenticated on any multi-node fleet — `route_public` forwards to the owner's peer listener before the handler runs, and the peer router mounts the same handlers under `Extension(PeerVouched)` so they skip `authorized_for` entirely. On a 3-node fleet two thirds of anonymous `POST /vol-agent/{o}/{n}/ref` calls rewrite volume history. Confirmed. Fix: delete `PeerVouched`; build `JobsState` once in `serve()` and hand the same `Arc` to both routers; the owner re-runs `authorized_for` on the forwarded headers (`Forwarder::forward` already passes them verbatim). Effort: S. Verify: a two-node test in `tests/routing.rs` that POSTs without a token to the non-owner and expects 401; `tests/vol_agent.rs` still green.
- [x] **Q-21** First-write region stamp is taken from `records[0].region` in the body, not from the token that authenticated — a region-A token can stamp a fresh volume as region B and lock A out. Fix: `authorized_for` returns the presented region; `append_commits` stamps from it and 400s a record whose `region` differs. Effort: S. Verify: unit test posting `record.region != token region` → 400.
- [x] **S-12 Q-22 I-5(part)** `client_ip` falls back to the first `X-Forwarded-For` hop, which the client sets — any path that reaches the pod without ingress-nginx (NodePort, in-cluster Service, the origin lock lapsing) turns `RUSTIC_GIT_AGENT_SOURCES` into a one-header bypass. Fix: delete the `.or_else(x-forwarded-for ..)` branch; `None` already fails closed for a bound region. Flip the test at `vol_agent.rs:323`. Effort: S. Verify: the flipped test.

**Repo create/delete on the api tier**

- [x] **Q-2** `POST /v1/repos` deletes an existing repository when the upstream create times out — a send error maps to `status = 0`, which falls into `other =>` and fires `/api/{o}/{n}/delete` on the owner (`crates/api/src/repos.rs:187-213`). **Git protocol correctness** — one PR across `crates/gitbase`, `crates/git`, `crates/api`

Register a key with UID `victim@…`, sign as the victim, badge reads verified. Confirmed. Fix: the one line `judge_ssh` has: `if !known.created_by.eq_ignore_ascii_case(author_email) { bad_email }`. Effort: S. Verify: unit test — registrant `bob`, UID `alice@`, author `alice@` → `unverified/bad_email`.
- [x] **S-7** Ref names are validated only on the push path — `gitbase::refs::update_refs` writes whatever name it is handed, and the browse-API merge/patch routes format `refs/heads/{b}` from the request body (`bins/server/src/browse_api/merge.rs:112,277,381`). Fix: move `valid_ref_name` from `crates/git/src/protocol/receive.rs:185` into `gitbase` and call it in `update_refs` for every `RefUpdate.name`; delete the copy. Effort: S. Verify: `POST /v1/repos/{o}/{n}/commits` with a newline in `newBranch` → 400; `git ls-remote` still clean.
- [x] **Q-8** Advertised `atomic` push is not atomic across connectivity failures — a ref that fails the closure walk is dropped from `owned` and the survivors are applied (`receive.rs:256-301`); the existing test passes only because a third ref fails later. Confirmed. Fix: after the loop, if any `results[i].is_some()`, mark every other update "atomic push failed", delete `this_push_pack`, skip `update_refs`. Effort: S. Verify: extend `atomic_push_rejects_whole_batch` to two refs, one with a hole.

**Workspace namespace and admission** — one PR in `crates/workspaces` + a migration note

**Git HTTP before authentication** — `bins/server/src/router/git.rs`

- [x] (step 1 done: `open()` before `to_bytes`, `RUSTIC_GIT_MAX_CONCURRENT_RECEIVE` semaphore, `tests/git_http_limits.rs`; step 2 streaming remains) **S-3 P-2 P-41(part)** `upload_pack`/`receive_pack` take `body: Bytes`, so axum buffers up to `max_body` (2 GiB default, 512 MiB deployed) before `open()` runs authn — a handful of anonymous concurrent pushes OOMs a srv pod and moves ownership. Verify: anonymous `POST git-receive-pack` with a 1 GiB body on a private repo returns 401 with the pod's RSS flat; `container_memory_working_set_bytes` during 3 parallel 500 MB pushes stays under the limit.
