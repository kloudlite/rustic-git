# Durable Snapshots Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A push takes a snapshot that outlives its workspace or environment; deleting a working copy removes only its live worktree and sync points; a volume is collected only when no working copy and no snapshot references it; the sync beat also cuts when the definition changes.

**Architecture:** References are Kubernetes ownership: a snapshot record is owned by the Volume, a sync point by its working copy, the Volume by each working copy. A finalizer on every Workspace/Environment drops the worktree and sync points, then removes its owner entry from the Volume only if a snapshot remains. The agent's beat sweeps bytes whose record is gone and volumes nothing references. `/v1`'s deletes and listing move to the CRDs. `spec.transient` is the only distinction; `spec.pinned` is dropped.

**Tech Stack:** Rust (kube-rs finalizers, JSON patch), btrfs via `Engine`, Next.js web (`bun test`).

**Spec:** `docs/superpowers/specs/2026-09-03-durable-snapshots-design.md`

## Global Constraints

- Vocabulary in every user-facing string, doc and web copy: workspace, environment, push, snapshot, restore, clone, delete; "sync point" only as the internal name of transients. No "commit", no "pin".
- A snapshot is `Snapshot.spec.transient == false`; `crd::Snapshot::is_snapshot()` is the one predicate, and it returns false for an old-build baseline (`transient: false`, `spec.parent == ""`, message `"migration baseline"`).
- Deleting a working copy never deletes a snapshot or its bytes; it deletes the worktree, the working copy's sync points, and the working copy's owner entry on the Volume iff a snapshot remains (any phase but Error).
- Ownership: snapshot → Volume (controller ref); sync point (sync, stop, clone, baseline) → its working copy; Volume → each working copy using it.
- The byte sweep deletes `snap/<name>` only after a fresh GET returns not-found; keeps on any error; runs in `spawn_blocking`; skips non-subvolumes.
- `retain` prunes sync points only; `WS_SNAPSHOT_KEEP` and the push-pruning arm do not exist.
- Deletes: `DELETE /v1/volumes/{name}/snapshots/{id}` → 404 unless owned; 409 `"a sync point cannot be deleted by hand"`; 409 `"this snapshot is the base of a running worktree"`; else delete the record, then delete the Volume iff it has no working copy and no snapshot left. `DELETE /v1/volumes/{name}` → 409 `"the volume still has a workspace or environment"` when a working copy exists, else delete.
- The sync beat cuts when the btrfs generation moved OR the derived definition differs from the newest Ready sync point's `spec.state`; environments included.
- Admission needs no change (spec-only policy; documented ceiling); agent RBAC `patch` on volumes already granted; api RBAC gains `snapshots: delete`, `volumes: delete` (table + rule + why).
- `deploy/k3s/crds.yaml` regenerated by `CRD_REGEN=1 cargo test -p rustic-git-workspaces --test crd_yaml`, never hand-edited.
- Comments say why; keep `// ponytail:` markers; commit subjects imperative sentence case; no tool attribution anywhere in commit messages.
- Gates, Rust: `cargo test -p rustic-git-agent-bin -p rustic-git-workspaces -- --test-threads=1; echo exit=$?` (unpiped) and `cargo clippy --workspace --all-targets --locked -- -D warnings`; web: `cd web && bun run lint && bunx tsc --noEmit -p apps/web/tsconfig.json && bun test`.
